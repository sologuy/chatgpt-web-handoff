# 输出要求
请在回答的最后，用一个 fenced code block 原样输出下面这段，字段名与顺序不要改；没有内容的列表写 `- none`：

**verdict 怎么定**（这三档有明确分工，别一律给 revise）：

- `pass` —— 按当前目标可以往下走了。**仍然可以有改进建议**，写进 `recommended_actions`
  就行，不要因为"还能更好"就压成 revise。
- `revise` —— 存在**具体的、会真的出问题**的缺陷：能说出在什么输入或什么状态下会错、
  错成什么样。说不出这两点的，不算 revise 的理由。
- `reject` —— 方向本身不成立，改细节没用。

`findings` 只放**会真的出问题**的东西。纯粹的改进空间、风格偏好、"理论上还可以更严谨"，
放 `recommended_actions`，不要挤进 findings 撑数量。

理论上存在但实践中未观察到、且已有合理余量的风险，写出来即可（注明是理论风险），
**不要因此改变 verdict**。

宁可少说三条无关痛痒的，也不要漏掉一条真的会炸的——但同样地，
不要为了显得严谨而把"能挑刺"包装成"有问题"。

`recommended_actions` 每条前面标出分量，**不要默认全写成「开工前必须先修」**：

- `[必须]` —— 不先做的话，后面的工作会白做或直接出错。说清楚为什么不能往后放。
- `[建议]` —— 该做，但可以和主线并行，或者做完主线再补。
- `[可选]` —— 锦上添花，不做也不影响。

真正的前置通常只有一两条，甚至一条都没有。把七八条都标成 `[必须]`，
接收方只能自己重新判断一遍，等于没给结论。
